# 国際化対応

このテンプレートはデフォルトで多言語対応をしておきたい。
どのように多言語対応をすればよいか、どのようなライブラリを使うとよいかなど、調査の上、デファクトスタンダードで今も開発、メンテナンスが継続されているものを選んでほしい。

言語設定に関しては、

1) ユーザーログイン後はユーザーの言語設定を見て表示（URLには言語を入れない）。画面に言語切替メニューを表示
2) ログイン不要なページでは、/en/ や /ja/ で言語切替で画面に言語切替メニューを表示

というようにしたい。ユーザーの言語設定はユーザーのテーブルに格納するイメージ

最初は en と ja に対応する

### 背景

このテンプレートは、FastAPI backend と React/Vite frontend を組み合わせたモノレポであり、現状の画面文言はほぼ日本語で直書きされている。frontend には i18n 関連依存はまだなく、`frontend/package.json` に `i18next` / `react-i18next` は存在しない。backend の `users` テーブルにも表示言語を保持する列はなく、`GET /api/auth/me` / register / login が返す `AuthUserResponse` は `id`、`email`、`roles`、`permissions` のみである。

要件では、認証後は URL に言語を入れずユーザーの言語設定で表示し、認証不要ページでは `/en/` や `/ja/` のように URL で言語を表す。したがって、表示言語の source of truth は画面種別で分ける必要がある。

- 認証済み画面: `users.language_code` を source of truth にする。
- 認証不要画面: URL の locale prefix を source of truth にする。
- 未ログイン状態から認証済み URL へアクセスした場合: ユーザー設定がまだ読めないため、public 側の推定 locale に基づく login URL へ redirect する。

調査結果として、TanStack Router 公式ドキュメントは optional path parameter による i18n routing を案内しており、`/{-$locale}/about` のような単一 route で `/about` と `/en/about` を扱える。今回の frontend は TanStack Router file-based route を使っているため、この方式が既存ルーターとの親和性が高い。React の翻訳ライブラリは `i18next` + `react-i18next` を採用する。`react-i18next` は React 向け公式 wrapper として `useTranslation` hook / `Trans` component を提供し、2026年時点でも changelog が更新されている。`i18next-browser-languagedetector` は公式 detector だが、今回の要件では URL prefix と DB user preference を明示 source of truth にするため、初期実装では採用しない。

参考:

- TanStack Router i18n: https://tanstack.com/router/v1/docs/guide/internationalization-i18n
- TanStack Router optional path params: https://tanstack.com/router/v1/docs/guide/path-params
- react-i18next: https://react.i18next.com/
- i18next TypeScript: https://www.i18next.com/overview/typescript
- i18next browser language detector: https://github.com/i18next/i18next-browser-languageDetector

### 方針とその理由

#### 1. 採用ライブラリ

`i18next` と `react-i18next` を frontend dependencies に追加する。

理由:

- React で広く使われている i18n スタックであり、hook ベースの既存コンポーネントと相性がよい。
- namespace、fallback language、interpolation、pluralization を段階的に使える。
- TypeScript の module augmentation により翻訳 key の型安全性を高められる。
- TanStack Router は i18n library-agnostic なので、route 側は locale 決定だけを担当し、翻訳処理を i18next に閉じ込められる。

採用しないもの:

- `react-intl`: ICU MessageFormat が主目的のアプリでは有力だが、今回の初期要件は en/ja の UI 文言切替が中心であり、既存コンポーネントへ段階導入しやすい `react-i18next` を優先する。
- `i18next-browser-languagedetector`: URL prefix と DB user preference の優先順位が明確なため、detector の自動保存や path 判定を入れると source of truth が増える。`/` など locale なし public URL の初期 redirect は小さな自前 helper で十分。
- Paraglide / Intlayer: TanStack Router 公式例では紹介されているが、既存 app に build-time 翻訳生成や別プロジェクト設定を追加するほどの要件ではない。まずは i18next の標準構成で始める。

#### 2. 対応言語と default

初期対応言語は `en` と `ja` のみとし、アプリ内部型は `LanguageCode = 'en' | 'ja'` に固定する。default は `ja` とする。

理由:

- 現在の UI 文言とテスト期待値が日本語であり、default を `ja` にすると既存挙動の変化を最小化できる。
- `/en/...` を明示した public page では英語を表示できるため、英語対応は URL prefix で確認可能。
- 将来 default を `en` に変える場合も、`DEFAULT_LANGUAGE_CODE` と root redirect helper の変更に閉じ込められる。

#### 3. DB 設計

`users` に `language_code TEXT NOT NULL DEFAULT 'ja'` を追加し、`CHECK (language_code in ('en', 'ja'))` を付ける。SQLModel 側も `server_default=text("'ja'")` を持たせ、`backend/alembic/env.py` の `compare_server_default=True` による drift 検出で落ちない状態にする。Python 側では `LanguageCode` 型と `SUPPORTED_LANGUAGE_CODES` を定義し、API request でも同じ値だけを受け付ける。

理由:

- 要件の「ユーザーの言語設定はユーザーのテーブルに格納する」に一致する。
- `TEXT` はこのプロジェクトの DB 設計指針に合う。
- boolean や数値ではなく `en` / `ja` の明示文字列にすることで、DB を見ただけで意味が分かる。
- `NOT NULL` にすることで、認証済み画面の言語決定で `null` fallback を考えなくてよい。

migration 方針:

- この repo は template として「未適用 migration chain を squash した単一の初期 schema revision」を正とする規約があるため、template 本体としては既存 `20260810_0001_initial_schema.py` へ統合する方針を第一候補にする。
- ただし、派生プロジェクトで既に `20260810_0001` が適用済みの場合は初期 revision の書き換えが危険になる。実装着手前に人間へ「template 規約どおり initial schema に統合する」か「適用済み DB 互換を優先して追加 migration `20260811_0001_add_user_language_code.py` を作る」かを確認する。
- CHECK 制約はこの repo では初導入になる。Alembic autogenerate / `db-check` は CHECK 制約差分を十分に検出できないため、integration test では `pg_constraint` で制約名の存在を確認し、許可外値を直接 INSERT して DB が拒否する挙動も確認する。制約定義文字列の完全一致には依存しない。
- 代替案として、CHECK なしでアプリ層 validation のみにする案と PostgreSQL ENUM 型を使う案を検討した。CHECK なしは DB へ不正値が入る余地が残り、ENUM は新言語追加時の DDL が重い。初期対応が `en` / `ja` に固定される現段階では、TEXT + CHECK を採用する。新言語追加時には `users` と OIDC state の CHECK 制約更新が必要になるため、その手順をドキュメント化する。

#### 4. API 設計

認証ユーザー response を `languageCode` 付きに拡張する。

- `GET /api/auth/me` response: `languageCode` を含める。
- `POST /api/auth/register` request: optional `languageCode` を受け取り、未指定なら `ja`。
- `POST /api/auth/login` response: DB の `languageCode` を含める。
- `PATCH /api/auth/me` request: `{ "languageCode": "en" | "ja" }` で現在ユーザーの言語設定を更新し、更新後の `AuthUserResponse` を返す。backend の PATCH 規約に合わせ、request model は optional field と `model_fields_set` で処理し、empty body は no-op 200 として現在の `AuthUserResponse` を返す。

理由:

- `PATCH /api/auth/me` は「自分の profile/preference の一部更新」として自然で、既存 `DELETE /api/auth/me` と同じ resource に収まる。
- unsafe `/api` request なので既存 CSRF middleware の対象になり、個別 CSRF dependency は不要。
- 更新後 response を返すことで frontend の auth cache を即時更新できる。

OAuth/OIDC の扱い:

- `GET /api/auth/oidc/{providerId}/start` に optional `languageCode` query を追加し、login page の locale を渡せるようにする。invalid `languageCode` は top-level navigation で 422 JSON を表示しないよう、422 ではなく `DEFAULT_LANGUAGE_CODE` へフォールバックする。
- `auth_oidc_authorization_states` に nullable `language_code` を追加する。`NULL` は「OIDC state に public locale を保持していない」ことを意味する。
- OIDC auto-provision で新規 user を作る場合は `oidc_state.language_code` があればそれを使い、なければ `DEFAULT_LANGUAGE_CODE` を `users.language_code` に保存する。
- 既存 user への login/link では user の既存 `language_code` を上書きしない。

理由:

- `/en/login` から OIDC で新規作成されたユーザーが、初回ログイン後に突然日本語へ戻る挙動を避けるため。
- OIDC callback は外部 redirect をまたぐため、frontend state や query だけに頼れない。既存の DB-backed state に持たせるのが既存設計に合う。
- 代替案として `redirect_path` から locale を導出する案も検討したが、この backend が保存している `redirect_path` は login 後の戻り先（例: `/app`）であり、`/en/login` 自体ではない。したがって auto-provision の初期言語を callback まで運ぶには、OIDC state に明示的に保存する方が正確である。

#### 5. Frontend 設計

`frontend/src/lib/i18n/` に i18n 初期化、言語型、JSON 翻訳ファイル、JSON resources 集約、URL helper を集約する。翻訳本文は TypeScript object ではなく JSON に置く。

予定ファイル:

- `frontend/src/lib/i18n/languages.ts`: `supportedLanguages`、`defaultLanguage`、`isLanguageCode()`、`normalizeLanguageCode()`。
- `frontend/src/lib/i18n/storage.ts`: safe localStorage wrapper。public preference と初回描画ヒントを分けて扱う。
- `frontend/src/lib/i18n/locales/ja/common.json`: 日本語の共通文言。
- `frontend/src/lib/i18n/locales/ja/auth.json`: 日本語の認証関連文言。
- `frontend/src/lib/i18n/locales/ja/landing.json`: 日本語の landing page 文言。
- `frontend/src/lib/i18n/locales/ja/app.json`: 日本語の認証済み app / settings 文言。
- `frontend/src/lib/i18n/locales/ja/admin.json`: 日本語の admin 文言。
- `frontend/src/lib/i18n/locales/en/common.json`: 英語の共通文言。
- `frontend/src/lib/i18n/locales/en/auth.json`: 英語の認証関連文言。
- `frontend/src/lib/i18n/locales/en/landing.json`: 英語の landing page 文言。
- `frontend/src/lib/i18n/locales/en/app.json`: 英語の認証済み app / settings 文言。
- `frontend/src/lib/i18n/locales/en/admin.json`: 英語の admin 文言。
- `frontend/src/lib/i18n/resources.ts`: 各 JSON を import して i18next resources として集約する。翻訳本文はここに直書きしない。
- `frontend/src/lib/i18n/i18n.ts`: i18next instance 初期化。
- `frontend/src/lib/i18n/LanguageSyncManager.tsx`: `__root.tsx` から常時 render する同期用 effect component。current language の唯一の書き手。
- `frontend/src/lib/i18n/publicLocale.ts`: public URL locale 取得、locale 付き URL 生成、`/` の fallback locale 推定。
- `frontend/src/lib/i18n/i18next.d.ts`: `CustomTypeOptions` module augmentation。
- `frontend/src/lib/i18n/formatters.ts`: `Intl.DateTimeFormat` など locale 依存 formatter を集約する。
- `frontend/src/lib/i18n/documentMetadata.ts`: `document.documentElement.lang`、`document.title`、`meta[name="description"]` を current language と同期する。
- `frontend/src/lib/i18n/DocumentMetadataManager.tsx`: `__root.tsx` から常時 render する metadata 同期用 effect component。

翻訳 namespace は初期実装では以下に分ける。

- `common`: Header、汎用 action、error state、language switcher。
- `auth`: login/register/OIDC/account deletion。
- `landing`: top page。
- `app`: `/app` と `/app/settings`。
- `admin`: admin top と user management。

理由:

- 画面単位に近い namespace にすると翻訳漏れのレビューがしやすい。
- 翻訳本文を JSON にすると、翻訳者や外部翻訳ツールに渡しやすく、将来 Crowdin / Lokalise などへ接続する場合も移行しやすい。
- TypeScript の `resources.ts` は JSON の集約だけに限定することで、翻訳本文と runtime wiring の責務を分けられる。
- 1つの巨大 object にすると差分が読みにくく、後続追加で conflict しやすい。

React component 外の翻訳:

- `frontend/src/lib/apiError.ts` は pure utility であり、`useTranslation()` を使えない。初期実装では `apiError.ts` から i18n instance を module-level import し、built-in error message を `i18n.t()` で解決する。
- built-in message は module 初期化時の `const` で文字列化しない。`toUserMessage()` の呼び出し時に `i18n.t()` を実行する関数または getter にし、`changeLanguage()` 後の current language に追随させる。
- 代替案として `toUserMessage()` が翻訳 key を返す案、または `toUserMessage(error, opts, t)` として `t` を注入する案もある。key を返す案は既存 call site の意味が変わり、`t` 注入案は login/register/settings/admin の全 call site に同じ boilerplate が増える。module-level import は依存方向が増えるが、変更範囲が小さく、React 外の utility でも同じ辞書を使えるため採用する。

言語状態の書き手:

- runtime の current language は `LanguageSyncManager` を唯一の書き手にする。`LanguageSyncManager` が public route locale、authenticated user の `languageCode`、localStorage の public preference、localStorage の描画ヒント、`navigator.languages`、default の優先順位から導出し、必要なときだけ `i18n.changeLanguage()` を呼ぶ。
- mutation、login/register handler、LanguageSwitcher の handler は `i18n.changeLanguage()` を直接呼ばない。これらは auth cache、URL、localStorage の明示 preference など、`LanguageSyncManager` が読む source を更新するだけにする。
- 理由は、宣言的な derived state と命令的な `changeLanguage()` を混在させると、URL 不変の authenticated 言語切替や login 後 redirect で一瞬の競合・ちらつきが起きやすいため。単一書き手にすることで、失敗時 rollback も auth cache / URL の状態だけを見ればよくなる。

テスト:

- i18n instance の初期化責務は `frontend/src/lib/i18n/i18n.ts` に置く。`frontend/src/test/setup.ts` は二重初期化せず、各 test の決定性のために `localStorage` を clear し、既存日本語期待値に合わせて `i18n.changeLanguage("ja")` で戻す。
- 翻訳 JSON の `ja` / `en` key 構造は再帰的に比較する unit test で守る。top-level key だけでは nested key の欠落を検出できない。

metadata:

- SPA なので runtime で `document.title`、`document.documentElement.lang`、`meta[name="description"]` を同期する。発火点は `frontend/src/routes/__root.tsx` から描画する `DocumentMetadataManager` component とし、`useRouterState()` で現在 route/path を読み、`useTranslation()` の current language 変化に追随して `useEffect` で同期する。
- TanStack Router の `HeadContent` / route `head` も検討したが、今回の title / description は route だけでなく i18next の current language と `/api/auth/me` 後の language sync に依存する。route match が変わらない language switch でも確実に更新するため、初期実装では `DocumentMetadataManager` を採用する。静的 route metadata を増やす場合は `HeadContent` への移行を別途検討する。
- `frontend/index.html` の `lang` / title / description は JS 初期化前の fallback として `ja` のまま残す。
- OG / Twitter card は通常クローラが JS 実行前の `index.html` を読むため、初期実装では locale ごとの動的切替対象外にする。必要になった場合は SSR / prerender / edge rewrite を別計画で扱う。

#### 6. Routing 設計

認証不要の主要ページは locale prefix 付き route に移す。

- landing: `/ja/`、`/en/`
- login: `/ja/login`、`/en/login`
- register: `/ja/register`、`/en/register`

互換 redirect:

- `/` は `detectPreferredPublicLanguage()` により `/ja/` または `/en/` へ redirect する。deterministic fallback は `ja`。
- `/login` は `/<preferred>/login` へ redirect する。
- `/register` は `/<preferred>/register` へ redirect する。

認証済み route:

- `/app`、`/app/settings`、`/admin`、`/admin/users` は URL に locale を入れない。
- 認証済み画面の表示言語は `queryKeys.auth.me` の `user.languageCode` と同期する。

優先順位:

- public localized route では、ログイン済みユーザーであっても URL の locale が常に勝つ。例: `languageCode: "en"` の user が `/ja/` を開いた場合、landing は日本語で表示する。
- authenticated route では、URL に locale を入れず、DB の `user.languageCode` が勝つ。
- locale のない public 互換 URL（`/`、`/login`、`/register`）では、`detectPreferredPublicLanguage()` で canonical locale 付き URL へ redirect する。

`/forbidden`:

- `/forbidden` は authorization failure 用の utility route として URL prefix なしで残す。
- user が読める場合は user の `languageCode`、読めない場合は `detectPreferredPublicLanguage()` の public fallback language で表示する。

理由:

- 要件の「ログイン後は URL に言語を入れない」と「ログイン不要ページは URL で言語切替」を両立できる。
- 既存 protected route の URL と redirect contract を大きく壊さない。

#### 7. 言語切替 UI

Header に `LanguageSwitcher` を追加し、常に表示する。

- public page では現在 URL の locale segment を切り替え、path/search/hash を保持する。
- authenticated page では `PATCH /api/auth/me` を呼び、成功時に `queryKeys.auth.me` cache を更新する。表示言語への反映は cache 変更を読んだ `LanguageSyncManager` が行う。
- 更新失敗時は form-level ではなく header 内の小さな alert として表示する。Dropdown menu は選択後に閉じるため、menu 内だけに error を置かない。
- 表示 label は `English` / `日本語` とし、button には `Languages` icon を使う。
- `LanguageSwitcher` は presentational component とし、内部で `useUpdateUserLanguage` や router navigation を直接呼ばない。Header 側で public / authenticated の handler を組み立てて渡す。
- mode 判定は pathname だけでなく、現在 route が public localized route か、`user` が存在するかを組み合わせる。`/forbidden` は未ログインでも直接到達できるため、user がなければ public fallback language の URL 非依存切替、user があれば authenticated preference 更新として扱う。

理由:

- 要件で public/authenticated ともに言語切替メニュー表示が求められている。
- Header は全画面共通で既に auth state を読んでいるため、user preference と public URL の分岐を置きやすい。

#### 8. 逸脱・トレードオフ

- 仕様では「ログイン不要なページでは `/en/` や `/ja/`」とあるが、既存互換のため `/`、`/login`、`/register` は削除せず、locale 付き URL へ redirect する。古い link や test entrypoint が即 404 になるのを避けるため。
- `i18next-browser-languagedetector` は初期採用しない。便利だが、cookie/localStorage/navigator/path の複数 source が自動で競合しやすく、今回の source of truth を曖昧にするため。
- 翻訳ファイルは TypeScript object ではなく JSON にする。TypeScript 直書きの方が `as const` による型推論は強いが、テンプレートとしては翻訳資産をコードから分離し、外部ツールや非エンジニアの編集に寄せる価値が高い。型安全性は `resources.ts` と `i18next.d.ts` の集約・module augmentation で補う。
- user preference 更新では audit log を追加しない。セキュリティイベントではなく通常 preference 更新であり、`users.modified_at` の更新で十分と判断する。
- admin user management に他ユーザーの language を編集する機能は初期スコープ外にする。要件は「ユーザー自身の表示言語」であり、管理 CRUD に混ぜると API/UI/権限の影響範囲が広がるため。
- 認証済み画面の初回描画で既定値 `ja` が一瞬表示されるフラッシュを減らすため、最後に解決した言語を `localStorage` に描画ヒントとして保存する。ただし source of truth は DB の `user.languageCode` であり、`/api/auth/me` 取得後に必ず DB 値で上書きする。
- logout 時は認証済み user 由来の描画ヒントを消し、未ログイン画面は public fallback language に戻す。代替案として最後の認証済み言語を維持する案もあるが、共有端末で前ユーザーの DB preference が残るため採用しない。

### 実装結果メモ（2026-08-12）

- `users.language_code` と `auth_oidc_authorization_states.language_code` は initial schema 更新で実装した。追加 migration は、現リポジトリ規約が未適用 migration chain を squash した initial schema を正とするため採用しなかった。
- `auth_oidc_authorization_states.language_code` の DB comment は当初案より短い `NULL means no public language preference was captured.` にした。理由は backend の `ruff E501` を避けつつ意味を保つため。
- `LanguageSwitcher` は `mode` prop を持たせず、public/authenticated の分岐を Header 側の handler に閉じ込めた。Switcher 本体は表示・選択通知だけを行うほうが副作用境界が明確で、`LanguageSyncManager` を唯一の current language 書き手にする方針とも整合するため。
- `useUpdateUserLanguage.ts` は新設せず、既存の `useAuthSession()` に `updateLanguage` mutation を追加した。既存 auth cache と logout policy が同じ hook に集約されており、追加 hook に分けるより query key 更新と描画ヒント破棄の契約を追いやすいため。
- `DocumentMetadataManager` は `__root.tsx` から常時 render し、`main.tsx` は変更しなかった。TanStack Router の `RouterProvider` が children を受け取らないため、router context と query context の内側で動かすには root route component が最適だった。
- legacy `/login` / `/register` の canonical redirect は `redirect({ href })` ではなく内部遷移の `to/search/hash` を使う形にした。TanStack Router では `href` redirect だと test 環境で hash が navigation option として保持されないため、path/search/hash を明示的に扱う設計へ寄せた。
- AuthMenu / login / register の相互リンクは `<a href>` ではなく TanStack Router の `<Link>` にした。SPA navigation を維持し、`redirect` search は Router の serializer に任せるため、生成 href は `/ja/login?redirect=%2Fapp` のように encode された値になる。
- `LanguageSwitcher` は更新失敗 error を menu 内に表示しない。Radix Dropdown は選択後に閉じるため、error は Header 側の menu 外 alert として保持し、trigger 自体は pending 中も開けるようにした。二重送信防止は menu item disabled で行う。
- `LanguageSyncManager` と Header の current language 導出は `resolveLanguage()` に一本化した。storage が空の未ログイン locale-less route では `navigator.languages` を見てから `defaultLanguage` に落とす。
- `apiError.ts` と `documentMetadata.ts` の `i18n.t(key as never)` は、扱う翻訳 key を union type にして cast なしで呼ぶ形へ変更した。

### 再々レビュー対応メモ（2026-08-12 追記）

- アカウント削除成功時も logout と同じく `clearLastResolvedLanguage()` を呼ぶようにした。account deletion は認証済み user の終了操作であり、共有端末で削除済み user の DB 言語が次の匿名セッションに残ることを避ける必要があるため。
