## 2. 総評 (論点別)

### 2.1 認証・DB のセキュリティ設計 — 【良い。水準以上】

認証コアの品質は高く、実装者が攻撃者視点を持っていることが読み取れる。以下は**変更せず維持すべき**設計:

- セッショントークンは 256bit 乱数を SHA-256 ハッシュで保存。平文は DB にもログにも残らず、それをテストで保証している (`test_auth_controller.py:100-112`)
- ログインのタイミング等化: ユーザー不在時もダミー Argon2 ハッシュを検証し、`is_active` チェックを `verify_password` の後に置いている。ダミーハッシュのパラメータが実 hasher と一致することまでテストしている (`test_auth_usecase.py:73-79`)
- login/register 時にセッションを再発行 (session fixation 対策)
- CSRF は double-submit + 認証済みリクエストでは `auth_sessions.csrf_token_hash` との timing-safe 突合
- ランダムトークン連打で監査ログを膨らませない工夫 (`_audit_known_rejected_session`)
- 監査ログ書き込み失敗時のロールバックや ContextVar の並行分離まで統合テストで検証

ただし「本番運用の前提」が甘い箇所が集中している (Secure cookie の既定、リバースプロキシ、Argon2 のブロッキング、CSRF のオプトイン方式 → P1-10〜P1-12, P1-14)。

### 2.2 拡張しやすさ — 【最大の弱点】

テンプレートの主目的に対して、現状の構造は追加コストが高すぎる。

- **CRUD エンドポイント 1 本の追加に約 14 ファイルの編集が必要** (新規 7 + 既存編集 7)。うち本質的なのは新規 7 ファイルと DI 登録 1 行だけで、残り (`__init__.py` 5 つへの追記、route.py、container.py の手動組み立て) はボイラープレート (P1-7)
- DI コンテナが全依存を `configure()` 内で手動 new しており、Injector の `@inject` 自動解決を使っていない。機能が増えるほど `configure()` が肥大化する (P1-7)
- controller が `request.app.state.injector.get()` のサービスロケータ方式のため、`dependency_overrides` によるテスト差し替えができず、controller の単体テストが 1 つも書けていない (P1-6)
- `transaction()` が `AuthRepositoryInterface` に生えており、リポジトリを 2 つ以上使うトランザクションが張れない。**権限管理追加の最大のブロッカー** (P1-13)
- フロントも同様: 認証必須ページの追加が「10 行の beforeLoad コピペ + allowlist 手動更新」の 2 箇所同期 (P1-18)

### 2.3 読みやすさ — 【概ね良いが、サンプルコードが手本になっていない】

- 命名・レイヤ分離は一貫しており、auth 実装は読みやすい
- 一方 **sample / healthz / create_app / Config は品質が低く**、auth と実装スタイルが乖離している。新規開発者 (や AI エージェント) は「どちらを真似ればいいか」判断できない。未使用 import、死にコード、`402: "Forbidden"` という誤ったステータスコードがサンプルに残っている (P2-19, P2-22)
- yapf 既定の 79 桁制限による不自然な折り返しが可読性を下げている (P2-23)

### 2.4 抽象化の適切さ — 【方向は正しいが、境界の引き方に歪み】

- interface 分離の意図は良いが、**必要な場所に抽象がなく、不要な場所に形骸化した抽象がある**:
  - 差し替えが確定している `InMemoryLoginRateLimiter` (AGENTS.md 自身が「本番は共有ストアへ」と明記) に interface が無く、具象クラスで DI 束縛されている (P2-24)
  - 逆に `GetSampleIndexUsecaseInterface` は 1 行の実装しかなく、interface の価値 (モックしてテスト) を示すテストも無いため二重定義にしか見えない (P3-8)
- `AuthenticatedSessionContext` が usecase 層の具象モジュールに定義され、controller がそれを直接 import している (レイヤ違反、P2-17)
- `register`/`login` の戻り値が型注釈のない 4 要素タプル (P2-18)

### 2.5 ドキュメントと実装の乖離 — 【テンプレートとして深刻】

エージェント運用前提のリポジトリなのに、正典 (AGENTS.md / スキル) と実装が複数箇所で矛盾している。**エージェントは書いてあることを信じるので、この乖離はそのままバグを生む**:

| 乖離 | 実態 |
|---|---|
| 「aiosqlite が非 auth の既定」(backend/AGENTS.md) | SQLite に接続するコードは 1 行も無い。全モデルが同一 metadata で、JSONB があるため SQLite では動かない (P2-4) |
| 「yapf 設定は pyproject.toml」(backend/AGENTS.md) | `[tool.yapf]` も `[tool.isort]` も存在せず既定設定で動いている (P2-23) |
| 「UseCase の handle() は async に統一」(references) | 唯一のサンプル usecase が同期 (P3-8) |
| 「shadcn 由来は `components/ui/` へ」(frontend/AGENTS.md) | `components.json` の alias は `atoms` を指し、`ui/` は存在しない (P3-14) |
| references の「repositories/ を今後追加」 | 実装は `services/` に置いたまま未決着 (P3-7) |

### 2.6 テスト — 【auth は厚いが、構造的な穴がある】

- auth の単体・統合テストは質が高い (タイミング等化・ロールバック・並行性まで)
- しかし `TEST_DATABASE_URL` 未設定だと**テストの 54% (34 件) が黙ってスキップされ、品質ゲートが緑になる** (P1-16)
- モデルとマイグレーションの整合を検証するテストが無く、実際に乖離が発生している (P0-1)
- controller・repository・sample・create_app のテストが無い。フロントも成功系とセキュリティ機構 (allowlist) のテストが無い (P2-34, P3-9)

## 3. 指摘事項 (優先度順)

### P0: 致命的 — 真っ先に直す

#### P0-1: モデルとマイグレーションが乖離しており、次の autogenerate が既存インデックスを削除する

- **場所**: `backend/app/models/user.py:16`、`backend/app/models/auth_session.py:15-16`、`backend/app/models/auth_audit_log.py:27-28` (対応マイグレーション: `backend/alembic/versions/20260418_0001_create_auth_tables.py:37-42, 60-65, 87-88`)
- **内容**: マイグレーションは 6 つのインデックスを作るが、SQLModel の metadata には 3 つしか定義されていない。以下がモデル側に欠落:
  - `uq_users_email_lower` (UNIQUE, `lower(email)`)
  - `uq_auth_sessions_session_token_hash` (UNIQUE)
  - `ix_auth_audit_logs_event_type`
  - さらに `users.is_active` の `server_default=sa.true()` もモデル側に無い
- **影響**: 次に誰かが `alembic revision --autogenerate` を実行すると `op.drop_index(...)` が生成される。適用すると (1) セッショントークンの一意性が消え `.one_or_none()` が `MultipleResultsFound` を投げて全リクエスト 500、(2) 重複メール登録が可能になりログインが壊れる。`create_user` の `EmailAlreadyRegisteredError` はこのユニークインデックスの `IntegrityError` に依存しているため、重複検出の最終防衛線も消える。**権限管理の追加は必ず autogenerate を伴うので、その前提条件として最優先で直すこと**
- **修正方法**:
  1. 3 つのインデックスをモデルの `__table_args__` に定義する:
     ```python
     class User(SQLModel, table=True):
         __tablename__ = "users"
         __table_args__ = (
             Index("uq_users_email_lower", text("lower(email)"), unique=True),
         )
     ```
     `AuthSession` に `Index("uq_auth_sessions_session_token_hash", "session_token_hash", unique=True)`、`AuthAuditLog` に `Index("ix_auth_audit_logs_event_type", "event_type")` を同様に追加
  2. `is_active` を `Column(Boolean, nullable=False, default=True, server_default=text("true"))` にする
  3. `alembic/env.py` の `context.configure` に `compare_server_default=True` を追加
  4. 再発防止として `tests/integration/test_migration_consistency.py` を新設し、`alembic.autogenerate.compare_metadata` (または `alembic.command.check`) で差分が空であることを assert する。`manage.py` に `db-check` コマンドも追加する

#### P0-2: SPA のディープリンクが本番で 404 になる

- **場所**: `backend/app/bootstrap/route.py:12`
- **内容**: `app.mount("/", StaticFiles(directory="static", html=True))` は index.html への任意パスフォールバックを行わない。TestClient 実測: `GET /login` → 404、`GET /` → 200
- **影響**: 本番ビルドで `/login` や `/app` をブラウザ直叩き・リロードすると全滅する。SPA + クライアントサイドルーティングのテンプレートとして機能しない
- **修正方法**: `StaticFiles` を継承した `SPAStaticFiles` を作り、`get_response` で 404 を捕捉して `index.html` を 200 で返す (ただし `/api` 配下は除外)。`route.py` に定義し WHY コメントを添える

#### P0-3: `static/` ディレクトリが無いとアプリが起動できず、パスが cwd 依存

- **場所**: `backend/app/bootstrap/route.py:12`
- **内容**: `StaticFiles(directory="static")` は初期化時に存在チェックをする。実測で `create_app()` が `RuntimeError: Directory 'static' does not exist` になることを確認。相対パスなので `backend/` 以外の cwd でも壊れる。docker-compose が `mkdir -p static &&` で回避している (`docker-compose.yaml:36`) のがこの脆さの証拠
- **影響**: clone 直後 (フロント未ビルド) にバックエンド単体が起動できない。テンプレートの第一歩で躓く
- **修正方法**: パスを `Path(__file__).resolve()` 基準で絶対解決し、存在しなければ mount をスキップして警告ログを出す (または `makedirs`)。`backend/static/.gitkeep` をコミットする。docker-compose の `mkdir -p static &&` は削除する

#### P0-4: サインアップ (register) UI が存在せず、認証機能が片肺

- **場所**: `frontend/src/lib/authApi.ts` (login/logout のみ)、`frontend/src/routes/` (`register.tsx` 不在)
- **内容**: バックエンドには `POST /api/auth/register` が 409/422/429 の返し分けまで実装済みなのに、フロントに対応する API 関数もページも無い
- **影響**: このテンプレートから作ったプロジェクトは、DB に直接 INSERT しないとログインすらできない
- **修正方法**: `lib/authApi.ts` に `registerWithPassword` を追加し、`routes/register.tsx` と `components/organisms/Auth/RegisterForm.tsx` を新設。エラーは 409「登録済み」/ 422「パスワード要件」/ 429「試行過多」で出し分け。成功時はセッション cookie が設定されるので `invalidateQueries({ queryKey: queryKeys.auth.root })` 後に `/app` へ遷移。Header の未ログイン導線に「新規登録」を追加。**着手前に P1-19 (クエリキー統一) と P2-30 (エラーメッセージ共通化) を済ませると二度手間にならない**

### P1: 重要 — テンプレートとして配布する前に直す

#### 【バックエンド: アーキテクチャ基盤】

#### P1-5: AsyncEngine が破棄されず、コネクションプールがリークする

- **場所**: `backend/app/bootstrap/container.py:38` (`_, session_factory = build_engine_and_session_factory()`)、`backend/app/bootstrap/create_app.py` (lifespan 不在)
- **内容**: engine を `_` で捨てており、`await engine.dispose()` を呼ぶ場所がアプリ側に存在しない
- **影響**: graceful shutdown 不能。統合テストではテスト 1 件ごとに `create_app()` が新しいプール (最大 30 接続) を作って捨てるため、テストが増えると PostgreSQL の `max_connections` を食い潰す
- **修正方法**: `binder.bind(AsyncEngine, to=engine, scope=singleton)` で DI 登録し、`create_app` に lifespan を実装して `yield` 後に `await app.state.injector.get(AsyncEngine).dispose()` を呼ぶ

#### P1-6: controller が DI をサービスロケータとして使い、テスト差し替え・型検査が効かない

- **場所**: `backend/app/controllers/sample_controller.py:20`、`auth_controller.py:103,113,148,199,243`、`auth_dependencies.py:40,53`
- **内容**: 全ハンドラが `request.app.state.injector.get(SomeInterface)` を各自で書いている。`Depends` を使っていないため (1) `app.dependency_overrides` でのテスト差し替え不能、(2) 型チェッカが戻り値を追えない、(3) DI 解決失敗がリクエスト時まで露見しない
- **影響**: 「usecase をモックして controller を単体テストする」という基本戦略が取れない。実際 controller 本体のテストが 1 つも無い。権限管理のロール別 dependency を追加する際も同じ壁に当たる
- **修正方法**: 汎用の解決ファクトリを 1 つ作り、全 controller をそれ経由に統一する:
  ```python
  # app/bootstrap/dependencies.py (新規)
  def inject(interface: type[T]) -> Callable[[Request], T]:
      def _resolve(request: Request) -> T:
          return request.app.state.injector.get(interface)
      return _resolve

  # controller 側
  async def login(
      usecase: AuthUsecaseInterface = Depends(inject(AuthUsecaseInterface)), ...
  ) -> AuthUserResponse: ...
  ```
  既存の `get_request_auth_settings` はこの汎用版に統合する

#### P1-7: DI コンテナが全依存を手動 new しており、機能追加コストが高すぎる

- **場所**: `backend/app/bootstrap/container.py:23-57`
- **内容**: `configure()` 内で依存グラフを手で組み立て、起動時に全インスタンスを即時生成している。Injector の `@inject` 自動解決を使っていない。scope 指定も不統一 (`GetSampleIndexUsecaseInterface` だけ `scope=singleton` 無し)
- **影響**: CRUD 1 本の追加に約 14 ファイルの編集が必要 (§2.2)。`configure()` は機能数に比例して肥大化し、並行開発でコンフリクトする
- **修正方法**:
  1. 各実装クラスのコンストラクタに `@inject` を付け、`binder.bind(Interface, to=ImplClass, scope=singleton)` のクラス束縛に切り替える (登録が 1 行になる)
  2. `session_factory` などファクトリ由来の値は `@provider` を持つ Module クラス (`DatabaseModule`) に切り出す
  3. Module をドメインごとに分割 (`CoreModule` / `AuthModule` / ...) し、機能追加時の編集を該当 Module 1 ファイルに閉じる
  4. あわせて `route.py` のルータ登録を `app/controllers/*_controller.py` の自動探索にするか、手順を AGENTS.md に明記する
  5. `__init__.py` の re-export (誰も使っていない) を廃止し、追記作業を消す

#### P1-8: エラーレスポンス形式が統一されておらず、宣言と実際も一致しない

- **場所**: `backend/app/controllers/sample_controller.py:10-14` (Status 形式を宣言)、`auth_controller.py` (FastAPI 既定の `{"detail": str}`)、`create_app.py` (例外ハンドラ不在)
- **内容**: sample は `{"success": bool, "message": str}` を宣言するが実際は `{"detail": "Not Found"}` が返る (実測)。auth は `detail` 形式。未捕捉例外のハンドラも無い
- **影響**: フロントが複数形式に対応せざるを得ず、新機能のたびに形式が増殖する
- **修正方法**: エラーエンベロープを 1 つ決めて `models/error.py` に定義し (機械可読な `code` を含む形式を推奨: `{"error": {"code": "...", "message": "...", "details": [...]}}`)、`create_app` で `HTTPException` / `RequestValidationError` / 未捕捉 `Exception` の 3 ハンドラを登録して全経路を正規化する。`Status` は healthz 専用に縮退させる。フロントの `ApiError` も追随させる

#### P1-9: `create_app` がミドルウェア・ロギング・docs 制御をすべて欠き、未使用 import が誤読を招く

- **場所**: `backend/app/bootstrap/create_app.py:1-15`
- **内容**: `CORSMiddleware` / `GZipMiddleware` を import だけして未適用。`environment` 引数未使用。ロギング初期化なし (usecase の `logger.info` は既定レベルでは出力されない)。`docs_url` 制御なし (本番でも `/docs` 公開)
- **影響**: 「CORS 設定済み」と誤読させるのが特に危険。将来誰かが安易に `allow_origins=["*"], allow_credentials=True` を足すと CSRF 防御 (同一オリジン前提) が全面崩壊する
- **修正方法**: (1) 未使用 import と `environment` 引数を削除、(2) `_setup_logging(config)` を実装、(3) `ENVIRONMENT == "production"` で `docs_url=None` に、(4) lifespan 実装 (P1-5)、(5) 例外ハンドラ登録 (P1-8)、(6) CORS は「有効化する場合は `allow_credentials=True` + ワイルドカード origin を絶対に併用しないこと (CSRF 防御が同一オリジン前提)」という WHY コメントを残す

#### P1-13: `transaction()` がリポジトリ内に閉じており、複数リポジトリをまたぐトランザクションが張れない

- **場所**: `backend/app/interfaces/services/auth_repository_interface.py:13-15`、`backend/app/services/auth_repository.py:25-29`
- **内容**: トランザクション境界がリポジトリのメソッドで、`session_factory` と `ContextVar` をリポジトリインスタンスが個別保持している。別リポジトリは別セッション・別トランザクションになる
- **影響**: **権限管理追加の最大のブロッカー**。`RoleRepository` を作った瞬間、「ロール付与 + 監査ログ記録」を原子的に実行できない。回避すると 12 メソッドの `AuthRepositoryInterface` がさらに肥大化する god-repository になる
- **修正方法**: Unit of Work を独立した抽象に切り出す:
  ```python
  class UnitOfWorkInterface(metaclass=ABCMeta):
      @abstractmethod
      def transaction(self) -> AbstractAsyncContextManager[None]: ...
      @abstractmethod
      def session_scope(self) -> AbstractAsyncContextManager[AsyncSession]: ...
  ```
  `ContextVar` はモジュールレベルに 1 つだけ置き (P3-2 も同時解消)、各リポジトリは UoW を注入されて `session_scope()` を借りる。usecase は `async with self._unit_of_work.transaction():` の中で複数リポジトリを呼ぶ。あわせて `authenticate_session` (現状 1 リクエストで 3 つの独立セッションを開く → P2-11) も単一トランザクションに畳む

#### P1-10: Argon2 のハッシュ計算が event loop をブロックする

- **場所**: `backend/app/usecases/auth_usecase.py:190` (`hash_password`)、`:244` (`verify_password`)
- **内容**: async 関数内から同期の Argon2 計算 (実測 約 32-34ms、m=64MiB/t=3/p=4) を直接呼んでいる
- **影響**: `/api/auth/login` は未認証で叩ける。単一 worker (manage.py の既定) では毎秒約 30 リクエストで event loop が飽和し、認証と無関係な全 API のレイテンシが悪化する
- **修正方法**: `password_hasher.py` に `asyncio.to_thread` (または `starlette.concurrency.run_in_threadpool`) でラップした `hash_password_async` / `verify_password_async` を追加し、usecase をそれに差し替える。同期版はテスト用に残す

#### P1-11: リバースプロキシ配下でクライアント IP が単一値に潰れ、レートリミットが全ユーザー共有になる

- **場所**: `backend/app/controllers/auth_dependencies.py:11-17`
- **内容**: `get_client_ip` は `request.client.host` のみを見る。XFF を信頼しない判断自体は正しいが、信頼できるプロキシからの `X-Forwarded-For` を採用する経路が用意されていない
- **影響**: nginx / ALB / Ingress 配下では全ユーザーの試行が単一 IP バケットに集約され、`AUTH_RATE_LIMIT_ATTEMPTS_PER_IP=20`/15分 を全体で共有 → **悪意ある 1 ユーザーが 20 回失敗するだけで全ユーザーのログインが 429 になる** (実質 DoS)。監査ログの IP も全行プロキシ IP になり調査に使えない
- **修正方法**: `AuthSettings` に `AUTH_TRUSTED_PROXY_IPS: str = ""` (既定空 = XFF 不信) を追加し、`request.client.host` が信頼リストに含まれる場合のみ XFF を右から信頼ホップ分遡って採用する。`.env.example` と backend/AGENTS.md に「プロキシ配下では必ず設定」と明記

#### P1-12: `ENVIRONMENT` 未設定だと本番で Secure 属性なしの cookie が発行される

- **場所**: `backend/app/config/auth.py:7` (`ENVIRONMENT: str = "local"`)、`backend/app/controllers/auth_controller.py:19-29`
- **内容**: TLS 終端がプロキシにある構成では scheme は http なので、判定は `ENVIRONMENT` のみに依存する。その既定値が最も緩い `local`
- **影響**: `.env` の置き忘れ・Secret 注入漏れという典型的な事故で `session_token` が Secure なしになり、平文 HTTP でセッションを窃取できる。アプリは正常動作するので気付けない。**セキュリティ既定値が危険側に倒れている**
- **修正方法**: `AuthSettings` に `AUTH_COOKIE_SECURE: bool | None = None` を追加し、`None` なら `True` (安全側) を既定にする。ローカルは `.env.example` の `AUTH_COOKIE_SECURE=false` で明示的にオプトアウトする

#### P1-14: CSRF 検証がルート単位のオプトインで、新規エンドポイントは既定で無防備

- **場所**: `backend/app/controllers/auth_controller.py:140, 191, 236` (`dependencies=[Depends(require_csrf)]` の個別指定)
- **内容**: 防御が「開発者が毎回 `Depends(require_csrf)` を書くこと」に依存している。テンプレートに追加される業務エンドポイントは書き忘れた瞬間に CSRF 無防備 (SameSite=Lax は保険であって設計上の防御ではない)
- **影響**: 「unsafe メソッドは既定で CSRF 検証を通る」という不変条件がコードで表現されていない
- **修正方法**: `require_csrf` を ASGI middleware (または全体 router の共通 dependency) に格上げし、GET/HEAD/OPTIONS は素通し、それ以外は常に検証。除外が必要なルート (将来の OAuth コールバック等) は明示的な許可リストで抜く

#### P1-15: `manage.py serve` が常に `reload=True` で、本番イメージでもそのまま動く

- **場所**: `backend/manage.py:10`、Dockerfile の CMD
- **内容**: reload が無条件 True。worker 数も指定不可
- **影響**: 本番コンテナで watchfiles が常時走り、シングルプロセス固定
- **修正方法**: `--reload/--no-reload` (既定は ENVIRONMENT から判定) と `--workers` オプションを追加。`port: str` → `port: int` に修正 (Typer の型変換に任せる)

#### P1-16: 統合テストが黙ってスキップされ、品質ゲートが実質機能していない

- **場所**: `backend/tests/integration/conftest.py:18-22` (`TEST_DATABASE_URL` 未設定で skip)
- **内容**: DB を立てずに `uv run pytest` を実行すると **29 passed / 34 skipped (54% スキップ)** で終了コード 0
- **影響**: AGENTS.md の品質ゲート「pytest を通す」が、auth の統合テストを 1 つも実行せずに満たせてしまう。エージェント運用では特に危険
- **修正方法**: (1) CI 用に `REQUIRE_INTEGRATION_TESTS=1` なら skip を fail に変えるモードを追加、(2) AGENTS.md の品質ゲートに「`docker compose up -d postgres` + `TEST_DATABASE_URL` 設定の上で skip 0 件を確認」と明記

#### P1-17: 画面滞在中のセッション切れ (401) がどこにも処理されず、ユーザーが行き止まりになる

- **場所**: `frontend/src/main.tsx:12` (`new QueryClient()` 既定設定のまま)
- **内容**: 401 での redirect は `/app` の `beforeLoad` にしかなく、ルート遷移時しか走らない。滞在中にセッションが失効すると全 API が `ApiError(401)` を投げっぱなしになる
- **影響**: セッション TTL は有限なので、開きっぱなしのタブで確実に起きる
- **修正方法**: `QueryClient` 生成時に `QueryCache`/`MutationCache` の `onError` で 401 を捕捉し、auth キャッシュを null 化して `/login?redirect=<現在地>` へ遷移する共通ハンドラを実装する。`defaultOptions.queries.retry` も明示する (401 で 3 回リトライしないように)。あわせて 403 (権限不足) の分岐もここで設計しておく (§5.1 の前提)

#### P1-18: 認証必須ページの追加手順が確立しておらず、2 箇所のコピペ同期を強いる

- **場所**: `frontend/src/routes/app.tsx:15-27` (guard ベタ書き)、`frontend/src/routes/login.tsx:55` (`allowList = new Set(['/app'])` ハードコード)
- **内容**: ページを増やすたびに (1) beforeLoad の 10 行コピペ、(2) allowlist への追記、の 2 箇所を手動同期する必要がある。忘れると「ログイン後に必ず /app に飛ぶ」という発見しづらいバグになる
- **影響**: テンプレートの最頻作業が暗黙知に依存。エージェントに任せると allowlist 更新漏れがほぼ確実に起きる
- **修正方法**:
  1. pathless layout route (`src/routes/_authenticated.tsx`) を作り、`beforeLoad: requireAuth` を 1 回だけ書いて認証必須ページを子に置く
  2. allowlist を列挙から汎用判定に変える: `const isInternalPath = (v: string) => v.startsWith('/') && !v.startsWith('//')`
  3. frontend/AGENTS.md に「認証必須ページの追加手順」を明記

#### P1-19: 同じ `/api/auth/me` を 2 系統のクエリキーで二重取得しており、キーが前方一致の親子関係になっている

- **場所**: `frontend/src/lib/authApi.ts:42-56`、`frontend/src/lib/queryKeys.ts` (`me: ['auth','me']` / `strictMe: ['auth','me','strict']`)
- **内容**: Header は `me` (401→null)、guard は `strictMe` (401→throw) を使うため `/app` を開くと同じ API が 2 回飛ぶ。キャッシュが独立していて認識がずれうる。`strictMe` が `me` の前方一致の子なので、`invalidateQueries({ queryKey: me })` が strict 側も巻き込む罠がある
- **影響**: 無駄なリクエスト + 将来の invalidate 事故。OAuth コールバック実装時 (invalidate が必須) に間違えやすい
- **修正方法**: `['auth','me']` の 1 本 (`fetchCurrentUserOrNull`) に統一し、guard は結果が `null` かどうかで判定する。`beforeLoad` の戻り値でユーザーを route context に載せると後の role 判定でも使える。`currentUserStrictQueryOptions` と `strictMe` は削除

#### P1-20: OAuth 追加前に `users.password_hash` を nullable にしておく

- **場所**: `backend/app/models/user.py:17-18`、`backend/alembic/versions/20260418_0001_create_auth_tables.py:27` (`nullable=False`)
- **内容**: 外部 IdP のみで登録したユーザーにはパスワードが無いため、OAuth 導入時にこの制約は必ず破綻する。ダミーハッシュ挿入での回避は「パスワードログインできないはずのユーザーがパスワード経路に乗る」アンチパターン
- **影響**: マイグレーションはまだ 1 本目 (`down_revision: None`) なので、今なら修正コストが最小
- **修正方法**: `nullable=True` に変更し、`login` 側に `if user.password_hash is None:` の分岐を追加 (その場合もダミーハッシュ検証を実行してタイミングを揃えた上で `InvalidCredentialsError`)

## 5. 将来拡張への指針

### 5.1 ユーザーごとの権限管理 (role / permission)

**前提条件 (先に済ませるべき修正)**: P0-1 (autogenerate の安全化)、P1-13 (UnitOfWork)、P2-17 (AuthenticatedSessionContext 移設)、P1-6 (Depends 化、ロール dependency のテストに必須)、P2-6 (naming convention、中間テーブルの制約名のため)、P1-19 (フロントのクエリキー統一)。

**スキーマ設計**:
- `roles` / `user_roles` (中間テーブル、複合 PK) の多対多を最初から採用する。`users.role` 単一カラムの誘惑に負けないこと (database-schema-design スキルの規約でもある)
- 細粒度が必要なら `permissions` / `role_permissions` を足す 4 テーブル構成。単純な admin/member 程度なら `roles` のみで開始し、コード側の `Permission` enum → role のマッピングで済ませるのが現実的
- 監査は既存の仕組みがそのまま使える: `AuthEventType` は `StrEnum` + `String(64)` なので `ROLE_GRANTED` / `ROLE_REVOKED` / `PERMISSION_DENIED` の追加にマイグレーション不要。付帯情報は `auth_audit_logs.detail_json` (JSONB) へ

**バックエンド実装**:
- ロール取得は `authenticate_session` が既に毎回呼んでいる `find_user_by_id` に `selectinload` で相乗りさせ、追加ラウンドトリップを発生させない (モデルに `Relationship` の前例が無いので、async での lazy load が `MissingGreenlet` になる点に注意し、eager load を規約化する)
- `AuthenticatedSessionContext` に `roles` を載せ、dependency factory を作る:
  ```python
  def require_roles(*roles: str):
      async def dep(ctx: AuthenticatedSessionContext = Depends(require_current_session)):
          if not set(roles) & set(ctx.roles):
              raise HTTPException(status_code=403, detail=...)
          return ctx
      return dep
  ```
- **`revoke_sessions_for_user(user_id)` を必ず同じ PR で追加する**。現状はセッション単体の revoke しか無く、権限剥奪・パスワード変更をしても既存セッションが最大 24 時間生き残る
- `AuthUserResponse` は既に User と分離された DTO なので、ロールの露出はここに足せば安全

**フロントエンド実装**:
- `AuthUser` 型に `roles` を追加 (バックエンドの `AuthUserResponse` 拡張が先)
- `useAuthSession` に `hasRole()` / `can()` を追加
- ルートガードは `_authenticated` レイアウト (P1-18) の下に `_admin` レイアウトを重ねる形で `requireRole` を差す
- **403 (ログイン済みだが権限なし) の画面が現状どこにも無い**。P1-17 の 401 グローバルハンドラ実装時に 403 分岐 (`/forbidden` 表示) も同時に設計すること

### 5.2 OAuth / OIDC クライアント (外部 IdP でのログイン)

**前提条件**: P1-20 (`password_hash` nullable 化、最重要)、P1-14 (CSRF middleware 化 — コールバックは `X-CSRF-Token` を付けられないため「明示的な許可リストで除外」できる構造が必要)、P3-12 (cookie ヘルパ統合 — `state`/`nonce`/PKCE 用の短命 cookie に再利用)、P1-19 (クエリキー統一 — コールバック後の invalidate を間違えないため)。

**スキーマ**: `auth_identities` テーブルを新設する:
- `id` (UUID PK) / `user_id` (FK) / `provider` / `provider_subject` / `email_at_link_time` / `created_at` 等
- `(provider, provider_subject)` に一意制約
- 既存 3 テーブルの流儀 (UUID PK、timezone-aware datetime) に揃える

**バックエンド設計**:
- `AuthUsecase` を分割する。`_replace_session` と `_calculate_session_expiry` は認証方式に非依存なので `SessionIssuer` として切り出し、パスワード認証 (`PasswordAuthUsecase`) と IdP 認証 (`OAuthUsecase`) がそれを共有する形にする。`AuthUsecaseInterface` も「セッション検証・CSRF (共通)」と「方式別」に分割
- フロー: `GET /api/auth/oauth/{provider}/start` (state + nonce + PKCE を短命 cookie に保存して IdP へ redirect) → `GET /api/auth/oauth/{provider}/callback` (state 検証 → code 交換 → ID トークン検証 → ユーザー解決 → 既存の SessionIssuer でセッション発行 → SPA へ redirect)
- コールバックの CSRF は OAuth の `state` パラメータが担う。`SameSite=Lax` はトップレベルナビゲーションで cookie を送るので現設定のままコールバックにセッション cookie が届く (Strict にしてはいけない)
- **アカウント自動リンクの罠**: 「IdP の email が既存ユーザーと一致したら自動リンク」は、IdP 側で email 未検証だとアカウント乗っ取りになる古典的脆弱性。`email_verified` クレームの確認を必須とする方針を、実装前に `documents/plans/` に明記すること
- 設定は `OAUTH_CLIENT_SECRET` に `pydantic.SecretStr` を使う (現 AuthSettings は全て平文型)
- ライブラリは自前実装を避け `authlib` を推奨 (ID トークン検証・JWKS キャッシュ・PKCE を任せる)。依存追加はユーザー確認の上で
- レートリミッタのシグネチャが `allow(ip, email)` の email 前提なので、`allow(*keys)` の汎用形への変更 (P2-24 の interface 化と同時) が必要
- `AuthEventType` への `OAUTH_LOGIN_SUCCESS` / `IDENTITY_LINKED` 等の追加はマイグレーション不要 (現設計が素直に効く)

**フロントエンド設計**:
- リダイレクト型フローは fetch ベースの `apiClient` の外側。`lib/authApi.ts` に `startOAuthLogin(provider, redirectTo)` を置き、`window.location` 遷移をそこに閉じる
- `/login` は「OAuth ボタン群 → 区切り線 → パスワードフォーム」の構成にし、`LoginForm` 自体は変更不要な形に (`AuthProviderButtons` を並置)
- コールバック着地用ルート (`routes/auth.callback.tsx`) で auth キャッシュを invalidate してから元のページへ遷移
- `?redirect=` の内部パス汎用判定 (P1-18) が state パラメータ往復の前提になる

### 5.3 テンプレートとしての育て方 (総括)

1. **「サンプル = 模範解答」に投資する**。現状の sample は何も教えていない。実用的な CRUD 1 リソース (P3-8) と、それを 3 ステップで複製できる手順 (可能なら `manage.py scaffold`) がテンプレートの価値を最も引き上げる
2. **規約はドキュメントではなくコードで強制する** (CSRF middleware、エラーエンベロープ、base model、naming convention、CI)。エージェント運用ではこれが特に効く
3. **AGENTS.md と実装の乖離をゼロに保つ** (§2.5)。乖離は人間には「些細な不一致」でも、エージェントには「誤った指示」になる
4. **セキュリティの既定値は常に安全側に倒す** (Secure cookie、CSRF、docs 非公開)。テンプレートの既定値は全派生プロジェクトに伝播する
